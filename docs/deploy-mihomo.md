# Запуск BETBOT на Linux-сервере с существующим Mihomo

Нужны Docker Engine, Docker Compose v2 и уже запущенный Mihomo. BETBOT получает Telegram, OpenDota и Polymarket через HTTP/mixed-прокси Mihomo. Группа и канал, обученная модель и отчёты переносятся вместе с каталогом `data`.

## Перенос

1. Остановите локальный `uv run betbot run` через Ctrl+C перед окончательным переключением. Один токен должен иметь один процесс polling.
2. Загрузите личный `betbot-server.tar.gz` на сервер по SFTP/SCP и распакуйте:

```bash
tar -xzf betbot-server.tar.gz
cd betbot-server
bash deploy.sh setup
```

Скрипт найдёт единственный запущенный контейнер с образом/именем Mihomo. Если кандидатов несколько или имя нестандартное, укажите его и **внутренний mixed-port или HTTP port**:

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}'
bash deploy.sh setup mihomo 7890
```

Порт на хосте, например `2080:7890`, здесь не нужен: используйте `7890`. Если настройки читаются из нестандартного пути и порт не найден, скрипт берёт 7890; явный третий аргумент заменяет это предположение. Если прокси требует логин/пароль, задайте свой URL в `deploy.env`, например `VPN_PROXY_URL=http://USER:PASSWORD@127.0.0.1:7890`.

`setup` собирает образ, исправляет владельца только каталога `data` и проверяет Telegram, OpenDota, Polymarket и наличие модели. Эта проверка не получает обновления Telegram и не отправляет посты. Запуск бота выполняется отдельной командой:

```bash
bash deploy.sh start
bash deploy.sh status
bash deploy.sh logs
```

Сохранённые настройки публикаций продолжают действовать. В Telegram откройте `/start`, проверьте «Куда публиковать», выбранные турниры и режим публикаций. Перепривязывать группу и канал не требуется.

Личный архив с `--include-env` содержит токен Telegram и данные приложения. Он не предназначен для GitHub или публичной раздачи. Образы собираются без `.env`, `.secrets`, подписки VPN и каталога `data`.

## Существующий VPN и другое приложение

Бот остаётся отдельным контейнером с собственными процессами и файлами. Он использует сетевое окружение существующего Mihomo через `network_mode: container:ИМЯ`. Это позволяет обратиться к его прокси по `127.0.0.1`, включая прокси, который слушает только локальный интерфейс. Если Mihomo работает в host mode, скрипт выбирает host mode для бота. Эти режимы описаны в [документации Docker](https://docs.docker.com/engine/network/#container-networks).

Скрипт не меняет конфигурацию, выбранные узлы, подписку или жизненный цикл Mihomo и другого проекта. Бот не публикует порты; ему не требуются privileged mode, NET_ADMIN или доступ к Docker socket. Его лимиты — 1 CPU, 1 ГБ RAM и 128 процессов. Общая нагрузка на сам VPN добавляется, а остановка Mihomo влияет на всех клиентов этого прокси.

В `deploy.env` сохраняется только адрес подключения к уже существующему прокси. Если включены правила Mihomo, они должны направлять домены `api.telegram.org`, `api.opendota.com`, `gamma-api.polymarket.com` и `clob.polymarket.com` в VPN. BETBOT всегда использует настроенный прокси; прямого запасного подключения у приложения нет. Решение прокси направить запрос DIRECT определяется самим Mihomo.

## Переключение между узлами

Переключение задаётся группами в конфигурации Mihomo. `fallback` выбирает доступный узел по порядку, `url-test` выбирает по результатам проверки задержки. Бот наследует работу той группы, через которую существующий прокси маршрутизирует его запросы. Для этой схемы не требуется повторно переносить подписку в контейнер бота. Подробности — [группы Mihomo](https://wiki.metacubex.one/en/config/proxy-groups/).

Посмотреть только порт, режим и типы групп, не выводя секретные поля:

```bash
bash deploy.sh inspect
# При нестандартном пути:
bash deploy.sh inspect mihomo /etc/mihomo/config.yaml
```

Наличие `fallback`/`url-test` в конфиге само по себе не подтверждает, что нужная группа сейчас выбрана. Это проверяется в панели самого Mihomo. Полный конфиг и содержимое подписки передавать не требуется; для разбора достаточно результата этой команды.

## Остановка, восстановление и обновление

```bash
bash deploy.sh stop
bash deploy.sh restart
bash deploy.sh check
```

Если Mihomo **пересоздан** другим проектом, выполните `bash deploy.sh restart`, чтобы бот присоединился к актуальному сетевому окружению. Если поменялось имя контейнера или порт, отредактируйте `deploy.env`. Обычный сетевой сбой обрабатывается клиентами и журналом доставок; неоднозначные отправки не дублируются.

На старте приложение ждёт доступности прокси до 180 секунд и завершает запуск при неуспехе. `restart: unless-stopped` поднимет процесс снова. Healthcheck проверяет свежий цикл worker; `unhealthy` сам по себе не заставляет Docker перезапустить контейнер. Состояние источников дополнительно видно в `/status`, логи — через `deploy.sh logs`.

Код можно обновлять через GitHub, а `data`, `.env`, `deploy.env` сохранять на сервере. Не извлекайте старый архив поверх актуальной серверной базы при обычном обновлении. После изменения кода повторите сборку и пересоздайте только BETBOT:

```bash
docker compose --project-name betbot --env-file deploy.env -f compose.yaml -f compose.mihomo.yaml build betbot
bash deploy.sh restart
```

Для новой согласованной копии данных из рабочей папки:

```powershell
uv run python scripts/package_server.py --include-env
```

Архив содержит согласованную копию SQLite через backup API; файлы WAL/SHM и heartbeat не копируются. Изменения, сделанные локальным ботом после момента копирования, в этот архив не входят. Остановите локального бота и пересоберите архив непосредственно перед окончательным переносом, если нужно сохранить самые последние данные.
